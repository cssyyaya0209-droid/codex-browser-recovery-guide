# 技术说明与验证依据

## 方案来源

在 Windows x64 的一次实测中，Codex 桌面安装包为 26.901.6511.0，浏览器运行配置标识为 26.901.51231。两个标识来自不同组件。本文不提供来源电脑的用户名、路径、进程编号或代理端口。

观察到两个现象：

1. 桌面启动会重新生成托管 MCP 配置，手工追加的环境项不能稳定保留。插件生成配置也可能被重写。
2. 只向桌面进程传入代理仍不足以消除延迟。指定环境变量的只读核对显示，桌面与 app-server 有代理，MCP 启动层缺代理，而下层 kernel/trusted Node 已有代理。

本机实现提供 `CODEX_NODE_REPL_PATH` 入口，因此可以选择一个包装程序来补齐 MCP 启动层的环境，再运行原版 `node_repl.exe`。

```text
专用快捷方式 → 启动脚本 → Codex 桌面进程
                            ↓
                 MCP 配置选择包装程序
                            ↓
                 原版 node_repl.exe → 浏览器

启动脚本和包装程序均从所在目录读取 proxy.txt。
```

原版程序仍负责沙箱及工具行为；包装程序不解析或改写 MCP 标准流，只管理自己新建的子进程树。方案未修改安装包、全局代理、用户/系统环境或安全策略。

## 配置行为

启动脚本从 `proxy.txt` 读取代理，设置进程级 HTTP_PROXY、HTTPS_PROXY、网络开关和合并后的 allowlist，并通过 CODEX_NODE_REPL_PATH 指定包装程序。包装程序独立读取同目录文件，避免依赖已经观察到可能丢失的父进程代理变量。

双方会校验配置为单行、本地、不带凭据的 HTTP 代理 URL；启动脚本还调用包装程序的 `--check-config` 比较解析结果。缺少配置或模板未填完时直接报错，不回退到隐藏的固定端口。

包装程序通过运行环境中的 NODE_REPL_NODE_PATH 查找同目录原版 node_repl.exe，并保留当前用户自带运行时目录校验。未推广到其他安装布局或平台。

修改 proxy.txt 后须重新预检查并完整重启，保证桌面与其子进程使用同一版配置。

没有内部计时证据把所有历史错误归为某个遥测请求。早期也出现过导航等待和偶发 ACL 初始化错误，这些现象不能仅凭代理修正一并宣称根治。

## v2.0 的变化

- 删除程序中的固定代理地址，改为与脚本共读 proxy.txt。
- 自动查找标准安装位置；多个 Node 运行时时要求明确指定，避免随意选版本。
- 运行日志只记时间、子进程编号和状态，不记录代理值、用户名或运行时路径；日志写入失败不影响已建立的 MCP 会话。
- 首页保留使用步骤，技术细节移入 docs。程序校验值仅保留在单独文件。
- 具体发布验证范围见 [验证说明](VALIDATION.md)。

## 稳定性边界

CODEX_NODE_REPL_PATH 的采用依据是已验证版本的本机实现，并非官方承诺长期稳定的跨版本入口。应用更新后应核对当前行为。官方通用 MCP 的 command、env、env_vars 定义可参考 [OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。
